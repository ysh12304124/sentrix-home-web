# Sentrix 人物角色推断与鲜活画像设计

## 1. 文档状态

- 状态：已由用户确认，等待实施计划。
- 日期：2026-08-21。
- 目标代码库：153 机器 `/home/asus/Github/Sentrix-Home-Web` 的 `psh` 分支。
- 首个验证空间：`album3-max`。
- 本设计只定义新增的人物记忆、角色推断、画像与交互契约，不授权修改其他相册或清理生产数据。

## 2. 背景与问题

当前人脸检测和聚类质量已经达到可接受水平。遗漏的小脸可以接受，现阶段不再以提高检测召回率为主要目标。产品瓶颈已经从「人脸识别是否准确」转为以下两项：

1. 相册会产生大量人物簇，逐簇要求用户命名和填写关系，治理压力过大。
2. 当前人物总结由观察数量、事件数量、常见地点和活动等字段拼接而成，描述客观但缺乏人物感，不能呈现一个从家庭相册中逐渐形成的鲜活人物形象。

153 当前代码已经具备：

- `buffalo_l` 人脸识别、人物簇及确认、拒绝、合并和拆分；
- 用户上传身份照片预置人物，后续自动匹配；
- 聚类后批量命名、家庭角色和人物关系维护的未提交实现；
- `event_participants`、`person_event_memory`、`person_patterns`、`semantic_profiles`、`semantic_claims` 和 `person_appearance_evidence`；
- 确认人物后重建事件参与者、衣着证据和人物语义画像。

但当前链路仍存在结构性缺口：

- 图片观察被限制为极短的场景字段，缺少人物级动作、互动和角色线索；
- 人物级二次视觉分析只提取衣着；
- `person_event_memory` 主要投影整个事件的活动和地点，没有记录人物在事件中的独特行为；
- 人物关系必须由用户填写，没有可审计的模型假设层；
- 人物画像没有独立的生成、证据编译、版本和反馈机制；
- 快速导入数据可能只有身份桥接，没有完整场景语义，后续画像缺少材料。

## 3. 已确认的产品决策

### 3.1 身份与相册边界

- 人物身份按相册隔离。同一个人在不同相册中保留独立人物实体，不自动合并。
- 其他相册中已经确认的姓名可以作为建议，但不能直接确认当前相册的人物身份。
- 第一阶段只处理 `album3-max`，不回填旧相册，也不改变其他相册的记忆。

### 3.2 用户参与方式

- 用户不需要在导入前填写人物名单。
- 系统在聚类完成后主动筛选核心人物、猜测相册主人和家庭/社会角色。
- 家庭角色与姓名分开维护：系统猜角色，用户确认或修改；姓名由用户填写。
- 用户可以只确认角色、暂不填写姓名，也可以只填写姓名、暂不确认角色。
- 现有的上传身份照片、逐簇确认和手工关系维护继续保留，作为识别失败或用户主动治理时的兜底方案。

### 3.3 人物范围

- 只主动处理跨日期或跨事件反复出现的核心人物。
- 一次性人物、低证据访客和单样本人物默认折叠，可以长期匿名。
- 系统不能把所有常见人物强制解释成家庭成员。

角色候选必须覆盖：

- 家庭角色：父亲、母亲、配偶、孩子、祖父母、兄弟姐妹、其他亲属；
- 社会关系：朋友、同事、同学、邻居、照护者、老师；
- 弱关系：亲友、访客、一次性人物、无法判断。

### 3.4 推断与画像边界

- 关系推断必须基于整张人物关系图统一求解，不能让每个人物簇独立猜测。
- 外观年龄、代际差异和性别呈现可以作为弱信号参与评分，但不能保存为确定事实或直接向用户展示。
- 未确认的角色和关系可以用于人物画像，但必须使用「可能」「似乎」「从照片看」等不确定措辞。
- 未确认推断不能进入正式关系图、确定性 Agent 查询或核心事实。
- 画像允许低风险、可纠错的人物印象，例如「爱热闹」「有仪式感」「经常照顾孩子」。
- 禁止推断健康、收入、宗教、民族、政治立场、性取向等敏感属性。

## 4. 目标与非目标

### 4.1 目标

1. 将需要用户主动处理的人物从全部人物簇压缩为少量核心人物。
2. 在用户没有预填人物名单和身份照片的情况下，生成可解释的相册主人、角色和关系候选。
3. 在记忆形成阶段保存人物级动作、互动、可见状态和叙事瞬间，为长期画像提供真实材料。
4. 生成温暖、自然、有一定大胆推断但可回溯和可修订的人物小传。
5. 支持新事件触发的增量画像更新，保留历史版本和用户反馈。

### 4.2 非目标

- 本阶段不提高人脸检测召回率，也不重做 `album3-max` 的人脸聚类。
- 不自动给人物命名。
- 不自动把模型关系写成正式关系。
- 不全量分析所有含人脸的图片。
- 不回填 `album1`、`album2`、`album3` 或其他 PhotoBench 空间。
- 不替换现有的客观 Observation、Event、SemanticClaim 和证据链。

## 5. 总体架构

```text
Asset / Observation / FaceCluster
              |
              v
      核心人物与事件候选
              |
              v
   代表照片选择与人物编号标注
              |
              v
  PersonMoment（人物瞬间与互动）
              |
              v
  跨事件人物主题与关系图聚合
          /               \
         v                 v
Role / Relationship    PortraitEvidencePack
    Hypothesis                 |
         |                     v
         |              Portrait Writer
         |                     |
         +------> 用户确认 <---+
                       |
                       v
          姓名 / 正式关系 / 锁定画像
```

现有客观记忆继续回答「照片中发生了什么」。新增人物解释记忆回答「这个人在这些家庭时刻中呈现出怎样的形象」。两者必须分层保存。

## 6. 记忆形成链路

### 6.1 阶段 A：保留现有快速证据

现有快速链路保持不变：

```text
图片 -> CLIP -> 人脸检测 -> 人脸实例 -> 人脸聚类 -> 快速 Observation
```

本设计不要求重跑人脸，不修改已经确认的人物实体和姓名。

### 6.2 阶段 B：补齐 `album3-max` 的事件候选

`album3-max` 当前有 355 个 Asset、355 个 Observation、941 个人脸实例、50 个有效人物簇和 7 个已确认人物，但没有 Event、Relationship、PersonEventMemory 或 PersonPattern。

事件候选使用现有数据形成：

- 拍摄时间窗口；
- 现有图片向量；
- 人物簇重合；
- 文件来源和相册边界；
- 可用的 EXIF 地点；
- 代表图片语义补全后的活动、场景和物品。

事件候选形成前不需要全量视觉重分析。先使用确定性时间分组和已有向量形成候选，再对候选代表照片做语义补全。补全结果可用于事件合并或保守拆分。

### 6.3 阶段 C：核心人物筛选

系统为每个有效人物簇计算核心度，但不修改人脸相似度阈值。核心度信号包括：

- 出现的不同日期数；
- 出现的不同事件数；
- 与其他核心人物的共现覆盖；
- 居家、出行、庆祝、日常等场景多样性；
- 是否已有高质量、多视角人脸；
- 是否已经由用户确认；
- 是否只在单一短时间片段出现。

第一阶段主动呈现不超过 10 个核心人物。阈值不足的人物进入「其他人物」折叠区，不阻塞相册完成状态。

### 6.4 阶段 D：代表照片选择

只对重要事件的代表照片做人物级视觉分析。选择策略应覆盖：

- 每个核心人物至少一个高质量正面或清晰样本；
- 每个重要事件最多少量代表图；
- 尽量覆盖不同日期、地点、活动和共同人物；
- 通过视觉向量去除近重复照片；
- 优先选择人物身体和互动可见的照片，而不是只有脸部特写的照片。

目标是减少 VLM 调用，同时避免画像只由单一场景形成。

### 6.5 阶段 E：人物瞬间提取

系统为代表图片生成带 `P1/P2/P3` 标签的人物框预览。标签只用于模型理解，不成为原始 Asset。数据库保存标签到 `face_instance_id` / `cluster_id` 的映射和原图证据。

VLM 对每个目标人物提取：

```text
PersonMoment
- id
- scope_id
- cluster_id / person_id
- event_id
- observation_id
- asset_id
- face_instance_id
- action_text
- interaction_target_ids
- interaction_text
- participation_style
- visible_affect
- social_role_cues
- narrative_note
- confidence
- model_name / prompt_version
- status
- created_at / updated_at
```

字段含义：

- `action_text`：该人物在这个瞬间具体做什么；
- `interaction_text`：与谁、如何互动；
- `participation_style`：主动组织、陪伴、照顾、共同参与、旁观、拍摄等；
- `visible_affect`：只描述可见表情和状态，不推断心理疾病或稳定人格；
- `social_role_cues`：与角色判断相关的弱线索；
- `narrative_note`：这个瞬间为何值得纳入人物小传。

`PersonMoment` 是 `model_interpretation`，不是正式事实。每条记录必须绑定原始照片、人物框和模型版本。

## 7. 角色与关系推断

### 7.1 相册主人候选

系统先为核心人物生成「相册主人/我」候选。信号包括：

- 是否经常出现在自拍或近距离拍摄中；
- 是否长期贯穿多日期和多类事件；
- 是否与多数核心人物存在稳定共现；
- 来源设备和相册拥有者线索；
- 在关系图中是否能形成一致的家庭结构。

用户只需确认一次相册主人，也可以选择「都不是」或「暂不确认」。

### 7.2 角色假设

```text
PersonRoleHypothesis
- id
- scope_id
- cluster_id / person_id
- relative_to_person_id
- role
- rank
- confidence
- evidence_event_ids
- evidence_moment_ids
- reason_summary
- status: suggested / confirmed / rejected / superseded
- revision
```

同一人物至少保留 Top-2 候选和「无法判断」，不能只输出一个强制答案。

### 7.3 两两关系假设

```text
RelationshipHypothesis
- id
- scope_id
- subject_person_ref
- predicate
- object_person_ref
- inverse_predicate
- confidence
- evidence_event_ids
- evidence_moment_ids
- reason_summary
- status: suggested / confirmed / rejected / superseded
- revision
```

推断必须满足图约束：

- 配偶、朋友、同事、同学、邻居和兄弟姐妹关系对称；
- 父母与孩子、祖父母与孙辈、老师与学生、照护者与被照护者使用逆关系；
- 同一人物不能同时成为相册主人的父亲和孩子；
- 年龄、代际和性别呈现只能作为弱评分，不能覆盖互动和时间证据；
- 证据不足时优先输出亲友、访客或无法判断，不能强制家庭化。

### 7.4 正式关系写入

只有用户确认后，系统才将假设投影到现有 `relationships`、`family_role` 和 `semantic_claims`。模型候选不能直接写入正式关系图。

用户修改角色或关系后必须：

1. 记录修订；
2. 将冲突假设标为 `superseded`；
3. 重新计算相邻人物的关系候选；
4. 重建相关事件参与者和人物记忆；
5. 重新生成受影响的人物画像；
6. 保留旧画像版本。

## 8. 身份、角色与姓名状态

当前单一 `confirmed` 状态不足以表达产品流程。设计上将三个维度分开：

```text
identity_state: clustered / stable / rejected
role_state: suggested / confirmed / rejected / unknown
name_state: anonymous / suggested_existing / confirmed
```

允许的组合包括：

- 人脸身份稳定、角色已确认、姓名仍匿名；
- 人脸身份稳定、姓名已确认、角色未知；
- 系统建议其他相册已有姓名，但当前相册仍未确认；
- 人物长期保持匿名访客。

在不破坏现有表的前提下，第一版可以通过独立假设表和属性字段渐进实现，不要求一次性重写 `entities.status`。

## 9. 鲜活人物画像

### 9.1 画像证据编译

画像 Writer 不读取全部原始 Observation，也不直接自由浏览相册。系统先生成有限、结构化的 `PortraitEvidencePack`：

```text
PortraitEvidencePack
- person reference and confirmed identity fields
- confirmed role and relationships
- suggested role and relationships with confidence
- representative PersonMoments
- recurring activities and places
- recurring interaction patterns
- visible affect distribution
- appearance themes
- changes across time
- contradictions and unknowns
- representative evidence IDs
```

证据包需去除近重复信息，平衡不同时间和事件，明确区分：

- 用户确认事实；
- 客观视觉观察；
- 模型解释；
- 未确认关系假设；
- 冲突和未知。

### 9.2 画像主题

画像生成前先形成可审计主题：

- 反复出现的生活活动；
- 在家庭活动中的参与方式；
- 与其他人的相处方式；
- 镜头前的可见状态；
- 穿衣和生活风格；
- 随时间出现的变化；
- 有代表性的家庭瞬间。

### 9.3 画像 Writer

人物画像使用 12B 模型生成温暖、自然、有一定大胆推断的家庭人物小传。姓名未确认时使用「这位家庭成员」或稳定的匿名标签；姓名和角色确认后重写。

Writer 必须：

- 以具体反复出现的瞬间和互动为主体，不以计数开头；
- 对模型解释使用「似乎」「从照片看」「给人的感觉」等措辞；
- 不把单张照片的偶然表现写成稳定性格；
- 不写禁止的敏感推断；
- 不虚构职业、地点、经历或家庭事件；
- 输出用于展示的正文和结构化主题；
- 为每个主题绑定代表证据。

### 9.4 画像版本

```text
PersonPortraitRevision
- id
- scope_id
- person_ref
- revision
- portrait_text
- themes_json
- evidence_ids_json
- trigger_type
- model_name / prompt_version
- status: active / superseded / user_locked
- user_feedback
- created_at
```

用户可以：

- 查看每段画像的代表照片；
- 反馈「像他」「不像他」；
- 直接编辑；
- 锁定画像或主题，避免后续自动覆盖；
- 查看历史版本。

## 10. 增量更新

画像不在每张图片导入后重写。只有以下情况触发：

- 新增重要事件；
- 某项行为或互动达到重复支持门槛；
- 出现新的关键关系候选；
- 新证据与当前主题明显冲突；
- 用户确认或修改姓名、角色和关系；
- 用户主动要求刷新画像。

更新时只重新分析新增或受影响的代表事件，复用既有 PersonMoment，再生成新的证据包和画像版本。

## 11. 用户界面

### 11.1 人物页

人物页按以下层级组织：

1. 「系统认为最重要的家庭成员」：不超过 10 人；
2. 「其他常见人物」：亲友、同事、同学、访客和无法判断；
3. 「一次性或低证据人物」：默认折叠。

核心人物卡展示：

- 代表头像；
- 跨日期和事件覆盖；
- 系统首选角色及置信度；
- 一个简短的匿名画像摘要；
- 「确认角色并填写姓名」命令。

### 11.2 角色确认

```text
人物 A
系统猜测：母亲 72%
其他可能：妻子 18% / 亲友 10%
姓名或称呼：[            ]
角色：[母亲 v]

[稍后处理] [不是核心人物] [确认]
```

角色确认和姓名填写独立保存。用户可以选择「无法判断」或非家庭角色。

### 11.3 关系图

关系图默认只显示用户确认的关系。模型建议通过单独的虚线或候选层展示，必须有明确的「建议」标识和证据入口。

### 11.4 人物画像

人物详情首先展示自然小传，然后展示：

- 画像主题；
- 代表照片和事件；
- 关系与互动；
- 最近新增的人物瞬间；
- 「像他 / 不像他 / 编辑 / 锁定」操作；
- 历史版本。

## 12. 兼容性与兜底

- 现有逐簇命名、批量命名、关系维护和身份照片预置入口继续可用。
- 现有客观 `semantic_claims` 和正式 `relationships` 的语义不改变。
- 模型假设写入新表或新属性，不复用正式事实状态。
- 现有 Agent 只读取已确认身份和正式关系；画像可作为带来源的软上下文，但不能覆盖事实查询。
- 任何新流程失败时，人物簇、原图和现有确认能力仍可独立使用。

## 13. `album3-max` 验证方案

### 13.1 基线

当前实测：

```text
assets                  355
observations            355
face_instances          941
active_face_clusters     50
confirmed_people          7
events                    0
relationships             0
person_event_memory       0
person_patterns           0
```

### 13.2 隔离原则

- 使用 SQLite backup API 创建验证副本；
- 不直接在生产数据库上试验迁移、角色推断或画像回填；
- 不重跑人脸检测和聚类；
- 冻结现有 7 人姓名和角色作为隐藏评测答案；
- 推断阶段不能向模型暴露隐藏姓名和角色；
- 验证结束后不自动覆盖正式人物数据。

### 13.3 执行顺序

1. 从现有 Observation、Asset、FaceInstance 和向量生成候选事件；
2. 为候选事件选择代表照片并补齐语义；
3. 提取 PersonMoment；
4. 筛选核心人物并生成相册主人候选；
5. 生成角色与关系图假设；
6. 与冻结的 7 人答案比较；
7. 恢复姓名和已确认角色，仅用于画像展示；
8. 生成匿名和实名两版画像；
9. 进行人工画像评审。

### 13.4 验收标准

- 50 个有效人物簇被压缩为不超过 10 个主要确认对象；
- 现有 7 个已确认核心人物全部进入主要候选；
- 家庭角色 Top-1 命中至少 4/7，Top-2 命中至少 6/7；
- 关系图不存在对称关系或逆关系冲突；
- 7 人均生成非计数式人物小传；
- 至少 5/7 的画像经人工判断为「像」或「基本像」；
- 所有画像主题都能回到照片、人物瞬间或事件；
- 禁止的敏感推断数量为 0；
- 其他相册和生产人脸数据未发生变化。

## 14. 失败处理与可观测性

- 事件候选、人物瞬间、角色推断和画像生成分别记录任务状态，允许单阶段重试；
- 每次模型调用记录模型、Prompt 版本、输入证据和解析错误，不记录秘密或凭据；
- 人物瞬间解析失败不阻塞客观事件和人脸功能；
- 角色图求解失败时退化为「无法判断」，不自动调用旧逻辑写入关系；
- 画像生成失败时继续展示结构化人物主题和原有客观摘要；
- UI 展示生成时间、证据覆盖和画像是否需要更新。
